BRAMBLELOOP FINAL MASTER UPGRADE
 v0.1 - Etsy Search, Listing Conversion & Search-Visibility Intelligence
STATUS: STARTED. Living final-upgrade file. Append future final audits before the final handoff.
Objective: turn Etsy's own current search guidance into executable Brambleloop requirements. The core model is two-stage:
query matching determines eligibility; ranking orders eligible listings. Search success therefore requires truthful relevance,
click-worthy creative, conversion, shop/listing quality, and customer-service trust - not keyword stuffing.
Audited source set: Etsy's Ultimate Guide to Etsy Search; Keywords 101; Add Attributes to Help Increase Your Shop's
Visibility. Because the Ultimate Guide explicitly delegates core mechanics to linked official guides, this audit also followed
Etsy's How Search Works, Well-Crafted Listing, Search Visibility, Listings That Convert, and Customer Service search-ranking
guidance.
1. DEEP AUDIT - OPERATING FINDINGS
Two separate search problems: Brambleloop must model query matching and ranking separately. A single SEO score can
hide whether a listing fails to match or matches but loses the ranking/conversion battle.
Holistic relevance: Titles are only one input. Etsy describes title, tags, attributes, descriptions, categories, first photo, reviews
and other shop/listing information as part of matching/ranking.
Structured data is search inventory: Specific categories and truthful attributes create matching/filter opportunities. Missing a
relevant attribute can exclude a listing from filtered results.
Use all 13 tags intelligently: Etsy recommends all 13 tags, varied multi-word phrases, long-tail terms, and avoiding repetition
of tags/categories/attributes.
Readable titles, not keyword soup: Lead with what the item is for mobile/search scanning. Etsy says title phrase position
does not itself change ranking, so front-loading is a buyer-comprehension rule, not a ranking myth.
Descriptions matter: Relevant phrases belong naturally in early description copy. Copying the title or dumping keywords is
discouraged.
Hero image is search infrastructure: The first photo earns the click. Etsy advises clear high-resolution imagery and warns
against confusing first-image collages/text-heavy thumbnails.
Conversion feeds ranking: Clicks, favorites and purchases contribute to engagement. Search optimization must therefore
include CTR and conversion experiments.
New-listing boost is a learning window: A new listing gets a small temporary boost so Etsy can learn shopper response.
Treat this as an evidence-collection window, not proof of demand.
Trust affects visibility: Shop icon, listing completeness, multiple strong images, policies, reviews, message response and
case rate matter to buyer confidence and search performance.
Search Visibility is first-party evidence: Etsy's Shop Manager Search Visibility recommendations should be ingested when
browser access exists; do not approximate first-party warnings with internal guesses.
Search rules change: Etsy explicitly says search changes. Brambleloop needs dated policy snapshots and automatic
re-audits.

3. REQUIRED ARCHITECTURE
SearchPolicySnapshot: Dated official-rule registry with source, retrieval date, extracted rule, applicability and supersession.
SearchIntentGraph: Product -> query families -> category/attributes/tags/title/description coverage, with provenance.
EtsySearchCertificate: Versioned certificate binding listing content hash to search/truth/creative/conversion readiness.
SearchExperiment: One-variable experiments with baseline, treatment, window, evidence volume, verdict and rollback.
SearchVisibilityFinding: First-party Etsy warning/recommendation captured from Shop Manager with lifecycle state.
SearchPerformanceFact: Observed impressions, clicks, favorites, orders and conversion where accessible; never fabricate
missing metrics.
ServiceQualityFact: Reviews, response SLA and case-rate evidence used as operational/search-health signals.
Policy Change Watch: Regularly re-fetch official Etsy guidance and invalidate affected assumptions when source text
materially changes.
4. RELEASE / ACCEPTANCE TESTS
 Listing with 13 tags but missing a relevant attribute must fail search certification.
 Listing with an irrelevant Christmas attribute must fail even if predicted impressions rise.
 Title keyword stuffing must lose to a clearer title when query coverage is otherwise preserved.
 Changing a hero image must invalidate click-readiness certification and re-run thumbnail QA.
 Changing category must re-resolve valid attributes and invalidate stale tags/coverage assumptions.
 Search Visibility warning cannot be marked resolved until the Etsy surface no longer reports it or a documented exception is
approved.
 Ads spend cannot be credited as an organic-ranking improvement.
 A new listing's temporary boost cannot be treated as demand proof until engagement/conversion evidence matures.
 Zero impressions/clicks must remain zero/unknown; never impute neutral performance.
 Search guidance older than the active policy snapshot must not silently override newer official Etsy guidance.

9. LAUNCH CONSEQUENCE
The benchmark purchase and physical-validation systems answer different questions. Benchmark teardown asks: is
Brambleloop's customer experience competitive? Physical/test evidence asks: does Brambleloop's own pattern actually
produce what it claims? The final launch architecture must satisfy both at the appropriate risk level.

P0 / launch-critical reliability standard. This addendum incorporates the production lesson in which the full test suite completed successfully

v0.13 Addendum - Autonomous Research Agent & Research-Before-Invention
Owner direction: Brambleloop must have a first-class Research Agent. When the system encounters a material unknown, stale assumption,

52. CONTINUOUS AUTONOMOUS BUSINESS IMPROVEMENT
Brambleloop is not complete merely because it can create and publish products. After launch, the system must continuously
collect real operating evidence and use it to improve the business. Launch establishes the production feedback loop; real
marketplace operation becomes part of the evidence system used to improve Brambleloop over time.
Non-delay rule. Continuous improvement must never become continuous launch delay. Once the defined launch-quality floor
and all launch-critical gates are genuinely satisfied, non-blocking improvements move to post-launch operation. The company
must sell, measure, learn and improve while operating rather than indefinitely expanding the pre-launch build.
53. ETSY STOREFRONT AS A CONTINUOUSLY OPTIMIZED SYSTEM
The Etsy storefront is an owned operating surface, not a static export target. Brambleloop must continuously evaluate listing
titles, tags, descriptions, attributes, SEO, thumbnails, image order, presentation, pricing, promotions, product/category
selection, shop organization, branding, merchandising, customer questions, reviews, refunds/cancellations, and listing state
using real evidence.
Where Etsy supports event delivery, webhook/event signals such as order paid, cancelled, shipped, delivered and
inventory/out-of-stock events should feed Brambleloop's event layer. These signals complement - not replace -
listing/search/conversion analytics and marketplace research.
54. CLOSED-LOOP LEARNING ARCHITECTURE
The required operating loop is: Etsy and other approved evidence sources -> durable event/data layer -> specialized
departments -> research/diagnosis -> bounded experiment -> validation/gates -> controlled deployment -> measured
outcome -> durable learning. The system must not equate 'self-improving' with uncontrolled self-modification.
Every autonomous change must preserve attribution: what changed, why it changed, what evidence justified it, expected
effect, measured result, whether it was retained or rolled back, and which requirement/department owned the decision. Failed
experiments remain durable knowledge so later agents do not repeatedly rediscover the same failure.

56. AUTONOMY, SAFETY AND OWNER-RESERVED BOUNDARIES
Agents may research, diagnose, propose, test and run bounded experiments automatically within their granted authority.
Product Truth, customer safety, legal/policy compliance, material financial exposure, destructive actions, publication/activation
and other owner-reserved boundaries remain gated according to the Master. Evidence-driven improvement may never
weaken an invariant merely to improve a metric.
57. ETSY EVENT / WEBHOOK OPERATING REQUIREMENTS
Etsy webhook integration is a post-authentication Commerce capability. It must be implemented with endpoint verification,
authenticated/validated event handling where supported, idempotency, duplicate-event protection, durable event storage,
retry handling, observability, replay/reconciliation strategy, and tests before production subscription. OAuth/shop authorization
and the controlled draft-image-update-readback-delete shadow round trip remain prerequisites; webhook work must not
distract from or bypass those gates.
58. LEARNING QUALITY STANDARD
Brambleloop should become materially better with accumulated operating history. At 3, 6 and 12 months, the system should
have stronger evidence for what to make, how to present it, what to charge, what customers value, what causes support
friction, and which experiments actually improve outcomes. Improvement is measured by validated business/customer
outcomes and preserved quality floors - not by commit count, agent activity or code volume.
59. ACCEPTANCE TESTS
 A paid-order event can enter the durable event layer once, be processed idempotently, update the appropriate business evidence, and
not create duplicate effects when replayed.
 An underperforming listing can be detected from evidence, assigned to the correct department, changed through a bounded experiment,
measured, retained or rolled back, and recorded with full attribution.
 A customer-support pattern or review issue can create a durable improvement candidate without silently rewriting Product Truth.
 Independent post-launch departments continue useful work in parallel when another lane is blocked, rendering, waiting on an external
system or awaiting an owner decision.
 A non-launch-critical improvement cannot keep launch in Shadow once every defined launch-quality floor and launch-critical
dependency is satisfied.
 A proposed optimization that violates a safety, policy, Product Truth, spend or owner-reserved gate is refused even if its conversion
metric is better.
 Failed experiments remain queryable and prevent automatic repetition unless new evidence explicitly justifies reopening them.

IMPROVEMENT
This section strengthens rather than replaces Build 2 and the existing F-001+ / F-501-F-513 Etsy requirements. The master already covers

Deep-audit findings
 Etsy is an operating surface, not merely a publishing endpoint. Shop Manager contains first-party evidence that internal guesses cannot
replace.
 Search Visibility is a first-party defect queue. Brambleloop should ingest warnings, fix them, and confirm Etsy clears them.
 Marketplace Insights is first-party demand intelligence. Etsy Plus currently provides unlimited searches, so BrambleloopStudio should use it
deliberately for product and keyword research.
 Etsy Plus is paid infrastructure: listing credits, Ads credits and customization should be measured and used only when they create value.
 Shop trust and customer-service quality affect conversion and search readiness; logo/icon, About, policies, reviews, response and case
health need explicit gates.
 HTTP success is not business success. Important writes require remote readback and field-by-field verification.
 Self-improvement includes the Etsy page itself: merchandising, branding, SEO, economics, service and policy health should continuously
improve from measured evidence.

55. COMPLETE ETSY SHOP MANAGER SURFACE AUDIT
This increment was triggered by direct inspection of the current BrambleloopStudio Shop Manager navigation. It extends v0.16 from a broad
Etsy operating system to an explicit surface-by-surface contract. The left navigation currently exposes Dashboard, Listings, Messages, Orders,
Etsy Search Visibility, Stats (including Shop Traffic and Marketplace Insights), Customer Service Stats, Policy Violations, Marketing (Etsy Ads,

Operating rule
Every Etsy surface must be classified as OBSERVE, ANALYZE, ACT, OWNER-ONLY, NOT-APPLICABLE or UNSUPPORTED. 'Not built'
and 'not applicable' are different states. A surface may be useful even when it cannot be automated: Brambleloop must still know it exists,
know what evidence it contains, and maintain the exact manual/owner action required.

71. PURCHASED-PATTERN AUDIT: MINI STAR STITCH CARDIGAN
This upgrade records the system-level lessons from a full audit of the purchased Mini Star Stitch Cardigan by MJ's Off The Hook
Designs. It does not copy the purchased pattern into Brambleloop's product catalogue. The purchase is treated as private benchmark
evidence for architecture, quality, merchandising, validation and workflow design.
Product architecture
10 child sizes (0-3 months through 12), oversized fit, DK #3 yarn, 5.0/5.5 mm hooks, optional hood, 4-6 buttons.
Construction
Worked flat in one piece from the bottom up. Back band/panel first; sleeve chains extend from both sides; neckline is
marked; fronts are completed separately; hood is added; garment is folded and seamed; cuffs and ribbed button band
finish the product.
Fabric identity
Star stitch is not merely a visual texture. It has explicit loop/eye/leg/base relationships, alternates with HDC return
rows, and has a measurable gauge of 18 stitches (9 stars) x 10 rows per 4 inches. Ribbing has its own SC-BLO
gauge.
Sizing truth
The source supplies chest, finished measurements, positive ease guidance, yardage, schematic dimensions,
sleeve/body/neck/hood measurements and size-specific stitch counts.
Customer support
The product combines a polished PDF, schematic, size chart, yarn substitution guidance, project tips, a step-by-step
video for the smallest size, a Learn Hub/community support funnel and gallery imagery.
Commercial system
The same design ecosystem is distributed across paid PDF storefronts plus a free blog/tutorial funnel and is
cross-sold into yarn, kits/collections and related designs.
72. NEW PERMANENT REQUIREMENTS - PRODUCT TRUTH AND STITCH IDENTITY
F-749 - Purchased Pattern = Benchmark Evidence, Not Product Source - A purchased competitor pattern may be used privately to
test ingestion, validation, rendering, merchandising quality and system capability. It is not authority to publish a copied, translated, lightly
modified, reformatted or derivative competing pattern.
F-750 - Instruction-to-Topology Compiler - Product Truth must represent construction order and relationships, not only final
silhouette. It must distinguish worked-flat, in-the-round, top-down, bottom-up, side-to-side, built-in sleeves, separate sleeves, joins,
seams, shaping, bands, hoods, pockets and other construction semantics.
F-751 - Stitch Semantics Are First-Class - Named stitches and stitch patterns must compile to explicit structural semantics where
commercially material. A texture label alone is insufficient when the product's appearance depends on loop placement, eyes, legs,
posts, BLO/FLO use, clusters, stars, cables, mosaic placement or similar structure.
F-752 - Stitch-Pattern Identity Gate - A generated listing image fails when the visible fabric is a different stitch pattern even if
silhouette, colour and garment features are correct. The gate must distinguish the intended stitch family/pattern from plausible-looking
generic crochet.
F-753 - Gauge Is Product Truth - Store stitch gauge, row gauge, hook/yarn context and separate ribbing/border gauges. Validate

F-754 - Multi-Gauge Regions - A product may contain multiple gauge regimes. Body fabric, ribbing, edging, cuffs, collars, bands and
decorative sections must carry their own gauge/stitch identities when the source specifies them.

complete size family before freezing a benchmark/render size. This catches indexing, parenthetical and grading errors that a one-size
parser can hide.
F-756 - Schematic Cross-Check - When schematics/measurement tables exist, reconcile them against stitch counts, gauge and
written construction. Disagreement becomes an explicit UNKNOWN/CONFLICT; do not silently choose whichever source makes the

F-757 - Optional Feature State - Optional hood, pockets, buttons, sleeves, colourways or other variants are explicit configuration state.
The listing image manifest must state which variant is being represented.
F-758 - Reference Defect Feedback Loop - If a generator faithfully reproduces a defect in Brambleloop's deterministic reference,

F-759 - Distinctive-Stitch Benchmark Set - Maintain adversarial positive/negative examples for each supported distinctive stitch
family. The validator must reject visually plausible but wrong alternatives before that stitch family is promoted to production support.

86. RUNTIME-PROOF DEFINITION OF DONE
F-831 - Capability Proof Chain - COMPLETE+PROVEN requires the applicable chain: requirement -> producer -> durable
evidence/state -> runtime consumer -> decision -> protected action/effect -> observable result -> independent proof.
F-832 - Existence Is Not Execution - A module, function, handler, cadence, row, dashboard card or unit test cannot by itself prove a
business capability operates.
F-833 - Live-Root Reachability - Runtime requirements must be reachable from real scheduler/API/worker/event roots; arbitrary callable
paths are insufficient.
F-834 - Consumption Required - Producing a reading is insufficient when the requirement exists to influence a downstream
decision/action; prove the consumer.
F-835 - Protected-Action Revalidation - Revalidate gates at consequential execution when authority/evidence can change after
planning.
F-836 - No Fixture-Only Proof - Injected test evidence with no production producer cannot prove end-to-end capability.
F-837 - Proxy Honesty - Heuristics/proxies stay labelled proxies and cannot silently satisfy direct-evidence requirements.
F-838 - Closure Integrity - Only an explicit valid park/gate removes executable work from OPEN. Defaults, stale labels or broad gate
tuples cannot hide reopened work.
F-839 - Final-Head Re-Audit - Material integration requires a new proof/reachability audit on the final effective source tree.
F-840 - Green Suite Necessary, Not Sufficient - A green full suite is mandatory but cannot replace requirement-level runtime proof.
