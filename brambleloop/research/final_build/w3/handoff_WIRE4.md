## F 5: UNKNOWN cost

- **Model.** `OwnerAction.max_cost_basis` is a new column, default `"stated"`, added by the additive migration. The new property `max_cost_known` returns None when the basis is UNKNOWN. `max_cost_cad` stays a non-null float, so existing Postgres needs no ALTER. The stored 0.0 for these rows is a placeholder that every reader must ignore.
- **Executor.** `approval_inbox` reads `max_cost_known`, so a card's cost is `None` with `max_cost_basis = UNKNOWN`. `_urgency` sorts an UNKNOWN cost after every stated cost, and such a card is never in `batched_free_and_quick`. `owner_queue.packet_for` keeps basis UNKNOWN for a None cost; this was a two-line edit to ops/owner_queue.py, which W3-HANG may also touch, so expect a possible conflict there. The packet is marked incomplete. Urgency reads "when costed".
- **Readers.** The dashboard shows "UNKNOWN (no ceiling stated yet)". `scale/war_room.py` and `launch/visibility.py` now serve None plus the basis. The CC approvals view already rendered None as null.
- **Finance.** `finance/accounting/policy._authority` refuses an owner action whose ceiling is UNKNOWN as spend authority.
- **Voice action.** `laura.agency.voice_selection.seed_owner_action(db)` is idempotent on `laura.voice.listen_shortlist`. It never re-opens a row the owner has answered. It runs at app startup in `main.py`, guarded.
- **Pre-existing issue, not fixed.** `_authority` treats a *stated* `max_cost_cad == 0` as uncapped (`if row.max_cost_cad and …`). That behaviour predates this lane and is outside the request. Flagged for lane E.
