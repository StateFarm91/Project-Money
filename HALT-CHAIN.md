# eng/halt-chain: rebuilds that start at certification now drive the whole chain

Base: `claude/w6-release-19h12`, which is production `f860904d`. This branch is not released yet.

## What production showed (evidence 2026-11-21T19:10Z)

Eleven halted products show the same `rebuild_outcomes` pattern:

- The retry attempt is done, and the only stage it ran is `gate.certify`. The chain reads `["gate.certify:done"]`.
- About 20 names are outstanding, for example certificate, chart, pdf, visual_truth, pricing, seo, listing_copy and marketing_asset. Of those, 11 read `superseded` and 9 read `stale`.
- Every verify pass leaves the names outstanding, so the `rebuild-incomplete` incident never closes and halt 380 stays open.

## Root causes

1. **The rebuild token stopped at certification.** `_targeted_rebuild` picks the earliest stage that remakes the outstanding classes. When `certificate` is outstanding, that stage is `gate.certify`, which was enqueued with `{"cir": ...}` only, without the rebuild token. Once certified, it enqueued `listing.draft` under the chain key `chain_key("listing", slug, version, release_hash)`, again without a token. Re-certifying an unchanged release gives the same release hash. So the key already belonged to the original chain's finished `listing.draft`, the enqueue deduplicated onto that job, and nothing after certification ran.

   Every stage after `listing.draft` already passes the `rebuild` token on. Only the step from certification to the listing draft dropped it. This explains the 11 products whose chain is only `gate.certify:done`.

2. **Superseded names were counted as outstanding.** The provenance check reads an artefact built from a release the product has since moved past as `SUPERSEDED`. No stage rewrites such an artefact, because the chain builds the newest release's artefacts under that release's own keys. Publication already refuses a superseded release, and the sentinel raises no halting incident for one. But the verify pass counted these names as outstanding. Even with root cause 1 fixed, the 11 superseded names would have kept the products' `rebuild-incomplete` incidents open for good.

## Fix

- **`runtime/release.py` `_targeted_rebuild`:**
  - `gate.certify` is now enqueued with `"rebuild": token`.
  - Superseded names are set aside on the request and verify passes, exactly like retired names. They are recorded under `superseded` in the outputs and in the `chain.rebuild_verified` audit, never counted as completed, and close nothing on their own. The incident closes only when every stale name has bound, verified completion evidence.
- **`runtime/pipeline.py` `handle_certify`:** reads `inputs["rebuild"]` and passes it into the `listing.draft` inputs and its `chain_key` token. With no token, the key is unchanged, so the normal chain behaves exactly as before.

Nothing is marked complete without being regenerated; completion still needs a bound, fresh row written by this attempt's stage job or a later one. Verify, child safety and every other gate are unchanged.

**Paid calls:** the extra stages can trigger `visual.image_production`, but that job's key is one per `slug@version@release`, without the rebuild token, so a rebuild does not buy images again. The paid FLUX gallery still starts only at for-sale admission.

## Proof

`tests/test_halt_chain.py` runs the real chain via `Worker.run_once`:

1. **A rebuild that starts at certification now re-runs the whole chain.** The test builds cloudline-baby-blanket, makes its certificate row and one marketing row stale, and requests a targeted rebuild for both.
   - The rebuild enqueues `gate.certify` with the token.
   - A new `listing.draft` runs with the same token, followed by `assets.build`, `pricing.position` and `listing.seo`, all with that token.
   - The marketing row is regenerated by this attempt.
   - The verify pass completes it, and nothing is left outstanding.
2. **A superseded name is set aside, not left outstanding.** It goes into `superseded`, the rest of the attempt still completes, and no `chain.rebuild_completed` row is written for the superseded name.

**Without the fix,** on base 19h12, test 1 fails at `certification of the rebuild enqueued no new listing.draft`. That is the production pattern.
